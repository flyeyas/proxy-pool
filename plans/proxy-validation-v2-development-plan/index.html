    代理检测 V2：开发计划与验收清单¶

    编制日期：2026-11-19（Asia/Shanghai）。

    状态：开发已启动；P0—P5 已有实现与分阶段测试，P6 验收进行中，P7 尚未执行。实测证据见 开发记录。

    设计依据：详细开发方案。

    代码基线：v1.5.1 / 6793a3cf9c544c345bcee996196d47a7a8028051。

    1. 执行原则与工期口径¶

    按一个主要开发者串行推进估算，不假定额外人员或并行 agent。基准约 10 个有效工作日，另留 2—3 日用于协议兼容、资源调优、公网观察和返工；这是工作量估算，不是从今天起自动执行的排期或固定上线承诺。每阶段通过验收门槛后才进入下一阶段。

    实施按阶段提交，未通过本地 Docker 验收不进入发布；服务器只使用 GitHub Actions 构建的镜像。不得跳过真实隧道、超时回收、鉴权、原子存储和回滚验证；未勾选事项按其完整验收条件继续验证，不因已有代码就视为完成。

    阶段 工作量 前置 阶段交付
    P0：基线与契约冻结 0.5 日 本方案 测试基线、字段/状态/API/配置契约、灰度路径
    P1：数据模型与候选 1 日 P0 规范化、多协议元数据、兼容来源
    P2：传输与 worker 2 日 P1 6 类 variant、真实 TLS/认证、硬超时、受控代理夹具
    P3：地区与结果策略 1 日 P2 地区策略、内容/状态分类、结构化事件
    P4：持久队列与状态 2 日 P3 Redis 原子队列、限流、租约、淘汰、熔断
    P5：API、采集路由与 WebUI 1.5 日 P4 兼容和 V2 接口、鉴权、筛选和可观测性
    P6：全链路与 Docker 1.5 日 P5 集成/资源/迁移/回滚报告、本地镜像验证
    P7：发布与服务器验证 0.5 日主动工作 + 观察窗口 P6 通过、进入实施发布阶段 Release、GHCR digest、影子报告、切换/回滚记录
    合计 10 日 + 2—3 日缓冲 — 完整可验收版本

    P0—P4 为检测后端里程碑 M1；P5—P6 为可交付里程碑 M2；P7 为上线里程碑 M3。只完成 M1 不能宣称完成整次升级。

    • [x] P0.2 冻结 endpoint/variant/profile、unknown 地区、失败分类、连续失败计数与默认分发语义；补充对象字段的可空、时间单位、枚举和派生规则。
    • [x] P0.3 冻结旧接口兼容范围及 V2 参数、认证范围、分页和错误结构；列出现有扩展 validator 的兼容行为。
    • [x] P0.4 固定使用“独立灰度入口 + 全局原子切换”，不设计线上两个引擎同时写同一 Hash；明确 Redis 为运行中 mode_epoch 的权威来源。
    • [x] P0.5 记录 CPU、可用内存、容器限制及已有服务的资源基线；服务器检查仅在进入实施后使用已授权连接，不在方案阶段启动测试。

    交付：版本化契约说明、基线测试报告、资源预算表、风险列表。门槛：地区/协议语义不混淆，所有新接口都有鉴权要求，部署切换无双 writer 窗口。

    3. P1：数据模型、地址标准化和采集兼容（1 日）¶

    • [x] P1.1 实现 ProxyCandidate、ProxyEndpointV2、VariantResult、TargetResult、ValidationPolicy；结果中保存 schema/policy 版本和 generation，未经检测为 unknown/pending。
    • [x] P1.2 实现 IPv4、方括号 IPv6、域名、端口、认证 URL 的标准化；明确 SOCKS4 IPv4 限制；敏感凭证只用引用进入任务和标识。
    • [x] P1.3 支持旧抓取器字符串与新结构化候选并存，跨批次合并来源和声明信息；历史 JSON 能读取，缺字段不崩溃，也不伪造 V2 成功。
    • [x] P1.4 Geonode 接入国家和原始协议提示，保留 SOCKS4/5；https 提示不直接等同 TLS 代理；其他采集源先经兼容适配器保持行为，再按需要补充元数据。
    • [x] P1.5 新增有限协议发现计划：有提示先验证，未知协议按配置逐步尝试；超预算未测项保持 pending。

    修改范围：helper/proxy.py、helper/fetch.py、fetcher/baseFetcher.py、Geonode 来源、新增 helper/validation 的模型和规范化模块。

    交付：地址与序列化单测、来源合并测试、混合协议源测试。门槛：相同地址不同认证不覆盖；同一 endpoint 多协议不丢失；旧来源无须全部重写即可继续运行。

    4. P2：真实协议传输与可回收 worker（2 日）¶

    • [x] P2.1 先做最小技术验证：现有 Requests 约束下的显式 urllib3/PySocks 版本组合；在 Python 3.13 镜像中验证 TLS-in-TLS、认证、SOCKS 和受控证书。验证不通过先调整传输封装，不靠关闭 TLS 检查通过。
    • [x] P2.2 实现 6 类 variant 的独立连接、精确代理 URL 和两层 CA 配置；采集路由共用 URL 描述，避免硬编码 http 或 https。
    • [x] P2.3 实现 GET 流式请求、手动白名单跳转、正文边界、响应关闭；禁止环境代理、系统 no_proxy、采集上下文代理和失败直连回退。
    • [x] P2.4 实现 spawn worker 生命周期、独立 Pipe、任务 heartbeat/状态事件；协调器统一落日志和写状态，worker 不写数据库。
    • [x] P2.5 实现剩余预算传递、暂态重试、整轮 30 秒截止与 2 秒回收；验证 DNS 阻塞、TLS 卡住、慢速持续回包和正文读取未完成均能回收。
    • [x] P2.6 实现受控 HTTP CONNECT、TLS 代理、SOCKS4/4a/5/5h、HTTPS 目标和测试 CA；夹具记录连接路径与域名解析发生处，测试网不依赖公网代理。

    交付：传输适配器、可运行测试夹具、逐协议实际链路报告、超时回收报告、依赖冻结结果。门槛：协议支持必须实际建立相应连接；强制错误 scheme 要失败；环境代理开启也不能掩盖坏候选；不存在持续增长的残留进程/FD。

    不接受以线程等待超时冒充网络调用已停止，也不接受只 mock head/get 为 200 就宣称协议集成完成。

    5. P3：地区、目标判定与日志（1 日）¶

    • [x] P3.1 实现地区证据优先级、成功/失败缓存、独立查询预算；支持 CN、非 CN、unknown 和可配置映射；保留主机与出口地区差异。
    • [x] P3.2 实现 QQ/Google profile 与结果分类：200 内容合格、受控重定向、403/429、验证码/同意页、TLS 错误、认证错误、证据不足。
    • [x] P3.3 实现 HTTP-only 可选检测；主准入不再依赖明文 HTTP 成功。明确海外仅 QQ 可达不得当作 overseas 合格。
    • [x] P3.4 实现事件 schema、批次汇总和递归异常脱敏；来源计数、endpoint、variant、attempt、最终结果分别统计。
    • [x] P3.5 固定现代但稳定的检测请求头，避免每次随机 UA 引入噪声；内容样本脱敏并版本化，仅保存必要测试片段。

    交付：分类单测、地区冲突用例、日志样本和批次统计对账。门槛：未知地区不误写 CN；非主目标成功不替代主目标；日志可说明“在哪个阶段、访问哪个目标、为什么没通过”。

    6. P4：队列、原子状态和目标保护（2 日）¶

    • [x] P4.1 新增独立 Redis V2 Repository，明确 key 前缀、序列化、过期与索引；禁止借用 DbClient 单例的 changeTable 在并发操作时切换命名空间。
    • [x] P4.2 实现 due 队列、有限候选读取、endpoint 去重、leader/endpoint 租约、owner 校验、generation/fence；真实 Redis 上验证原子领取和提交。
    • [x] P4.3 定时与手动入口统一生产任务；实现全局 2 请求/秒/目标、burst=1、重试/跳转/健康探测同额度，排队等待和请求耗时分开计量。
    • [x] P4.4 实现连续 3 个独立硬失败轮次、成功清零、首败暂停、10 分钟新鲜度、隔离和 TTL 清理；未测项目/基础设施错误不进入失败计数。
    • [x] P4.5 实现目标健康窗口、参考代理、open/half_open/unknown、canary 和分批恢复；区分代理端硬错误与共同目标/环境错误。
    • [x] P4.6 实现原子 pop/delete 与在途任务作废；删除后旧结果不能复活，重复领取/重启不能重复提交。
    • [x] P4.7 实现幂等迁移、legacy/shadow/active 模式、待发布策略与生效策略、兼容投影、过期清理和模式切换脚本；失败保持旧服务。

    交付：真实 Redis 8 并发/故障测试、状态转换表、恢复与迁移记录。门槛：两个入口同时触发不突破全局上限；429 不等于连接死亡；目标共同异常不批量删库；操作可中断并恢复。

    9. P7：GitHub 发布与服务器切换¶

    • [x] P7.1 确认所有验收证据对应同一提交；更新建议版本 v1.6.0 和变更日志，检查无 .env/Token/凭证/测试卷进入提交。
    • [ ] P7.2 推送 GitHub，分支 CI 全部通过；补足 tag 的测试门禁，再创建版本标签与 GitHub Release。tag 若已存在，不能强制移动覆盖已发布版本。
    • [ ] P7.3 等待 tag 对应的 GitHub Actions amd64/arm64 构建完成，核对 OCI revision、标签、架构与镜像 digest；发布记录引用固定 digest。
    • [ ] P7.4 使用受保护部署配置中的已授权 SSH 目标和端口，检查实际部署目录、Compose 项目、数据卷和生效配置；备份 Redis、旧 Hash、配置及旧镜像 digest。真实连接信息不写入公开仓库，路径和运行状态须重新确认。
    • [ ] P7.5 只更新应用镜像到 GitHub digest，先运行 shadow；Redis 8 和数据卷不重建，先验证登录、Token、WebUI、调度心跳和 legacy API。
    • [ ] P7.6 独立灰度入口先覆盖 10% endpoint、最多 50 个，至少观察 30 分钟；再扩大到 50% 和全量 shadow，比较分类和资源。覆盖率、可用量及故障解释达到门槛才允许切 active。
    • [ ] P7.7 暂停旧检测 writer 并排空在途任务；冻结回滚备份，准备受限 HTTP 投影；通过原子 mode_epoch 和投影切换完成全局 active，逐批复检剩余 pending。线上 Hash 不双写。
    • [ ] P7.8 切换后至少观察 30 分钟，记录新旧可用数变化、Google/QQ 失败类型、worker/RSS/FD、队列延迟、429、目标状态、接口鉴权和容器重启次数；发布最终部署记录。

    灰度流量比例指测试入口/影子候选覆盖，不让线上一部分 endpoint 被旧引擎、另一部分被新引擎无约束同时写入同一 Hash。全局切换点只有一个，必须可审计。

    停止扩大灰度的条件：连续出现真实路由错误/凭证泄露；环境代理导致假成功；目标故障触发批量删除；原子 pop 重复返回；已删除代理被旧任务复活；资源超过预算；配置丢失；无法解释的可用数明显下降。安全性/一致性缺陷立即停止并回滚，普通目标受限先隔离诊断。

    10. 强制验收矩阵¶

    ID 场景 必须观察到的结果 类型
    A01 普通 HTTP 代理访问 HTTPS 真实 CONNECT 和目标 TLS；记录 http + supports_https 协议集成
    A02 TLS 代理访问 HTTPS 代理、目标两层 TLS；分别验证证书 协议集成
    A03 SOCKS4/4a 正确协商；IPv4 限制与远端域名解析符合所选 variant 协议集成
    A04 SOCKS5/5h IPv4/IPv6、用户名密码及本地/远端 DNS 可区分 协议集成
    A05 将 HTTP 代理错误当 TLS 代理 明确协议错误，不产生成功记录 负向集成
    A06 HTTP 阶段失败但 CONNECT HTTPS 成功 允许对应主目标通过，不受旧前置条件阻挡 回归
    A07 同一 endpoint 支持多个协议 各协议结果独立；一次失败不覆盖其他成功 状态
    A08 CN、非 CN、HK/MO/TW、unknown 按 profile 选目标，原始地区码不改写 策略

    11. 交付证据目录与阶段完成标准¶

    实施过程中新增日期化验收报告，建议保存到 docs/reports/，只提交脱敏摘要和必要截图，不提交 Redis 原始备份、凭证、完整公网响应或机器专属 .env。

    每份报告应包含：日期与时区、提交、实际镜像/基础镜像 digest、Python/Node/Redis 版本、配置摘要、执行用例 ID、通过/失败/未执行、失败解释、资源曲线摘要和未关闭风险。发布报告再补 GitHub Release、Actions run ID、部署 digest 与回滚点。

    12. 回滚操作次序¶

    1. 停止扩大灰度，记录故障 batch/round 和当前模式，不先删除日志。
    2. 暂停生产者与协调器，吊销 leader/endpoint 租约并推进 mode_epoch，阻止迟到提交。
    3. 停止 worker，确认不再有 V2 结果写入；保存当前 V2 命名空间供复盘。
    4. 恢复部署前记录的旧应用镜像 digest 与 legacy 模式，不重建 Redis。
    5. 按需要恢复冻结的旧代理 Hash；runtime 配置只恢复本次 validation 相关字段，保留新增 Token 和其他用户变更。
    6. 启动旧规则复检，检查登录/Token、旧 API、调度心跳、采集开关和挂载数据。
    7. 记录回滚结果及后续修复范围；再次发布必须使用新的受测提交/版本，不覆盖原 tag。
